CustomPerm — Vérification du fix AT

Procédure ciblée pour valider que l'Access Transformer corrige bien le bug du wrapper qui ne retient pas son override.

Total : 0 Réussis : 0 Échoués : 0 En attente : 0

Résultats à coller dans le chat

Sélectionne tout (Ctrl+A), copie (Ctrl+C), et colle dans la conversation.

Préparation :
  1. Stoppe l'ancien serveur (stop).
  2. Relance avec .\gradlew.bat runServer — gradle re-build avec le nouvel AT (~30 s).
  3. Reconnecte le client sur 127.0.0.1 une fois le serveur prêt.

Phase A — Vérification au démarrage

CRITIQUEA.1 — L'AT a bien été appliqué (pas de log d'erreur)

Dans les logs au démarrage du serveur, il NE doit PAS y avoir de ligne du type :

[CustomPerm] Requirement write FAILED to stick on /XXXX (AT not applied?). Wrapper will not work.
Si tu n'en vois aucune → AT appliqué, le wrapper est correctement installé sur toutes les commandes. Continue.
Si tu en vois une ou plusieurs → AT non appliqué. La reflection écrit dans le vide, le wrapper ne marchera pas. Capture-les ci-dessous, on devra basculer en Mixin.
A.2 — Backend LP + abonnement event toujours actifs

Confirme que ces deux lignes apparaissent (comme avant) :

[CustomPerm] LuckPerms detected — using LuckPerms backend.
[CustomPerm] Subscribed to LuckPerms UserDataRecalculateEvent for live command tree resync.

Phase B — Test critique : commande directe pour un non-op

B.1 — Setup du scénario
deop Dev
customperm command add gamemode
lp creategroup vip
lp group vip permission set customperm.command.gamemode true
lp user Dev parent add vip
Attendu : chaque commande répond Successfully... sans erreur. La ligne [CustomPerm] LP user data recalculated for Dev doit toujours apparaître après la dernière commande.
CRITIQUEB.2 — /customperm debug doit afficher la dernière ligne en VERT
customperm debug Dev gamemode

Avec le fix AT, le rapport doit maintenant être :

=== Debug for /gamemode (Dev) ===
  Command exists in dispatcher : true
  In granted-commands list    : true
  Source has op level 2       : false
  Source has op level 4       : false
  PermService says customperm.command.gamemode : true
  Logical decision (computed) : true
  Actual wrapper canUse()     : true     ← EN VERT, plus de MISMATCH
Si la dernière ligne est en VERT et égale à true → le fix marche, le wrapper est bien installé.
Si encore MISMATCH → l'AT n'a pas pris malgré tout. On passera en Mixin.
B.3 — Reconnect + tester /gamemode en jeu

Déconnecte le client (Save and quit to title) puis reconnecte sur 127.0.0.1. Une fois en jeu :

/gamemode creative
Attendu : la commande passe et tu passes en mode créatif. Dev n'est pas op et n'a aucun perm vanilla — c'est UNIQUEMENT le wrapper qui autorise.

Phase C — Test du wildcard (qui plantait avant)

C.1 — Exposer plusieurs commandes et donner le wildcard
customperm command add give
customperm command add effect
customperm command add time
lp group vip permission set customperm.command.* true
Attendu : chaque commande répond Successfully.... Comme Dev est déjà dans vip, il hérite du wildcard.
C.2 — Tester les 3 commandes wildcard en jeu

Reste connecté (le re-sync auto pousse le nouveau tree). En jeu :

/give @s diamond 64
/effect give @s minecraft:speed 30 5
/time set day
Attendu : les 3 commandes passent. Si oui, le wildcard fonctionne avec le nouveau modèle.

Phase D — Test de révocation (ne plantait que par effet de bord)

D.1 — Retirer le grade et vérifier le refus
lp user Dev parent remove vip
customperm test Dev customperm.command.gamemode
Attendu : customperm test retourne DENIED.

Côté client (toujours connecté grâce au re-sync auto) :

/gamemode creative
Attendu : refus immédiat (la commande disparaît de l'autocomplétion). Cette fois, c'est bien la révocation LP qui bloque, pas l'absence d'op.

Verdict global

  • A.1 PASS + B.2 PASS + B.3 PASS → fix AT validé, on continue avec la procédure complète.
  • A.1 FAIL (warnings « FAILED to stick ») → AT pas appliqué, je passe en Mixin.
  • B.2 FAIL (encore MISMATCH) → l'AT a été appliqué mais d'autres effets bizarres. Je creuse selon la sortie.
