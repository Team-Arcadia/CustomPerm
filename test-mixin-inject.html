CustomPerm — Vérification Mixin @Inject sur canUse

Approche : on n'écrit plus dans le champ requirement (impossible à cause de l'inlining JIT). À la place, on intercepte la méthode canUse entière via Mixin.

Total : 0 Réussis : 0 Échoués : 0 En attente : 0

Résultats à coller dans le chat

Sélectionne tout (Ctrl+A), copie (Ctrl+C), et colle dans la conversation.

Préparation :
  1. Stoppe l'ancien serveur (stop).
  2. Relance avec .\gradlew.bat runServer — gradle re-build, ~30 s.
  3. Reconnecte le client sur 127.0.0.1.

Phase A — Build et chargement

CRITIQUEA.0 — Le build a réussi
Attendu : BUILD SUCCESSFUL ou démarrage du serveur direct.
CRITIQUEA.1 — Mixin chargée + tracking actif

Au démarrage du serveur, regarde les logs et confirme :

[CustomPerm] LuckPerms detected — using LuckPerms backend.
[CustomPerm] Subscribed to LuckPerms UserDataRecalculateEvent for live command tree resync.
[CustomPerm] Tracked N command nodes for permission gating.
La 3e ligne avec un nombre > 0 prouve que le tracking marche. Note ce nombre — un MC vanilla 1.21.1 a typiquement 50-150 nodes selon les datapacks.
Si tu vois des erreurs Mixin (FAILED to apply mixin, Could not find target method canUse, etc.) → capture-les ci-dessous.

Phase B — Test décisif : /customperm debug

B.1 — Setup
deop Dev
customperm command add gamemode
lp creategroup vip
lp group vip permission set customperm.command.gamemode true
lp user Dev parent add vip
Attendu : chaque commande répond Successfully.... La ligne [CustomPerm] LP user data recalculated for Dev apparaît à la fin.
CRITIQUEB.2 — La dernière ligne du debug doit être VERTE
customperm debug Dev gamemode
=== Debug for /gamemode (Dev) ===
  Command exists in dispatcher : true
  In granted-commands list    : true
  Source has op level 2       : false
  Source has op level 4       : false
  PermService says customperm.command.gamemode : true
  Logical decision (computed) : true
  Actual wrapper canUse()     : true     ← EN VERT, plus de MISMATCH
Si VERT → la Mixin intercepte bien canUse, le système marche.
Si encore MISMATCH → la Mixin ne s'applique pas comme attendu. Cas peu probable mais possible si la signature ne match pas. Capture la sortie.

Phase C — Test côté client

CRITIQUEC.1 — /gamemode marche pour un non-op avec perm LP

Déconnecte/reconnecte le client sur 127.0.0.1. En jeu :

Attendu : passage en créatif. Tu n'es pas op et tu changes de mode — c'est exactement ce que le mod doit permettre.
C.2 — /gamemode visible en autocomplétion

Tape /g dans le chat — /gamemode doit apparaître dans les suggestions.

Phase F — Révocation immédiate

CRITIQUEF.1 — Retirer le grade et tester
lp user Dev parent remove vip
customperm test Dev customperm.command.gamemode
Le test doit retourner DENIED.

Côté client (sans reco) :

/gamemode creative
Attendu : refus immédiat ET disparition de /gamemode de l'autocomplétion. Cette fois, on prouve que c'est BIEN la révocation LP qui bloque (pas juste le fait d'être non-op), parce qu'on vient juste de voir la commande passer en C.1.

Verdict

  • Tous les CRITIQUES en PASS → fix validé, le mod est fonctionnel. On peut passer aux tests complets.
  • A.0 FAIL → erreur compile. Capture le message complet, je corrige les imports / annotations Mixin.
  • A.1 FAIL (Mixin error / 0 nodes trackés) → la config Mixin ne s'applique pas. Probablement un problème dans customperm.mixins.json ou neoforge.mods.toml.
  • B.2 encore MISMATCH → la Mixin ne capte pas canUse (signature mismatch ou le @Inject ne s'applique pas). On regardera la logique d'injection.
  • C.1 FAIL alors que B.2 PASS → souci de re-sync côté client. La commande est techniquement autorisée mais pas dans l'arbre client.
  • F.1 PASS de la mauvaise façon (commande refusée mais on ne sait pas si c'est par notre système) → si C.1 PASS et F.1 PASS, c'est forcément que la révocation marche.
